## 二、主线:能力,不是省钱

**这条主线的外部依据**:2026 年 2 月,Karpathy 公开宣布自己 2025 年提的 "vibe coding" 已经过时,接替词是 **agentic engineering**。转变的实质是一句话——**从"给模型写提示",转向"工程化模型工作的那个环境"**。

同一时期圈内共识性话题(2026-05~07 调研,详见第六节)几乎全部落在同一根轴上:上下文工程、规范强制(Hooks)、规格驱动、循环工程、harness 大于模型。没有一条是"怎么省钱"。

**省钱是副线**。额度烧得快是真痛点,但它是能力不到位的**症状**,不是病。能力上去了,额度问题自动缓解;只治额度,下个月照样烧。所以本系列把成本写成每篇里的**约束条件**,不做主轴、不做入口。

**系列承诺(一句话)**:
读完这 10 篇,你从"会给 AI 提需求"升级到"会给 AI 建环境"——同一个人、同一批工具、同样的额度,产出不在一个量级。

## 三、结构:能力十阶,三段跃迁

能力不是知识点的堆叠,是**控制半径**的三次扩张。每一阶解决上一阶解决不了的那类失败。

| 阶段 | 篇号 | 控制半径 | 这一阶结束时你能做到 |
|---|---|---|---|
| **第一阶 · 单会话不失控** | 01-03 | 一次对话 | agent 在单个任务里不跑偏、不失忆、不乱翻文件 |

## 第一阶 · 单会话不失控(01-03)

### 01 · 你不是在写提示词,你是在给 AI 建工作环境
**免费公开 · 系列入口与能力证明**

**痛点场景**:同一个模型,同一个需求,别人一次过,你改五轮还不对。你以为差距在提示词写得好不好——不是。

**为什么常规做法不 work**:
- "提示词技巧"这条路 2026 年已经走到尽头。Karpathy 2026 年 2 月亲手宣布 vibe coding 过时,换词为 agentic engineering,转变的实质就是从"提示模型"到"工程环境"
- 提示词是**一次性的**:这次说清了,下次醒来它又不知道。环境是**持续的**
- 你脑子里的约定,对 agent 等于不存在

**做法(本篇正文)**:
- 一个 agent 的产出质量由四件东西决定,提示词只占一份:**环境(它能看到什么)、契约(它必须遵守什么)、循环(它怎么自查)、记忆(它记得什么)**
- 把这四件东西对应到你已有的工具:CLAUDE.md / AGENTS.md、Hooks、测试与验收、知识层
- 现场演示一次对照:同一需求,裸提问 vs 环境就位,差在哪一步开始分岔
- 十阶能力自测:你现在停在哪一阶(对应后面 9 篇)

**交付物**:**Agent 工程能力自测表**(10 项,每项对应本系列一篇,当场知道自己缺哪块)

**钩子**:自测表上多数人第一项就挂——agent 根本不知道该看哪些文件。这是第 02 篇。

---

### 02 · 上下文工程:让 agent 只看该看的那一层

**痛点场景**:让 agent 改一个函数,它先把半个项目读了一遍;或者反过来,它没读关键文件就动手,改出来的东西对不上。

**为什么常规做法不 work**:
- "把规则都写进 CLAUDE.md" 是错的方向。2026 年圈内的共识反过来:**规范文件越长,遵守率越低**,长上下文会稀释注意力
- 有 Anthropic 工程师公开演示过大幅精简 system prompt 而效果不掉的案例(单源,建议自己在项目上复测,不要当定论直接抄比例)
- 上下文不是越大越好:注意力稀释 + 成本双杀

**做法**:
- **渐进披露**三层骨架:根级 CLAUDE.md 只写全局铁律和 gotchas → 目录级文档写模块约定 → 文件头摘要写这个文件干什么
- CLAUDE.md 的正确写法:写"这个项目的坑在哪",不写"通用编码规范"(那是模型已经会的)
- 按需加载:什么该常驻,什么该按路径门控,什么该做成调用时才展开的能力包
- 判断标准:agent 开工前读了几个文件——这是可量化的
- 副线(成本):全仓扫读是最大的单笔开销,这一篇顺手把它按下去

**交付物**:**三层文档骨架模板** + 一份 CLAUDE.md 瘦身对照(该留/该删/该下沉)

**钩子**:文档写对了,agent 还是会不听。因为文档是"请求",不是"强制"。这是第 03 篇。

---

### 03 · 建议与强制:为什么写进规范的东西 agent 照样不遵守

**痛点场景**:CLAUDE.md 里明明写了"不许直接改 main"、"提交前必须跑测试",agent 该犯还犯。

**为什么常规做法不 work**:
- markdown 文件是**建议**,模型可以权衡、可以遗忘、可以在长会话里丢掉
- 加粗、全大写、"IMPORTANT"、写三遍——都只是提高优先级,不改变性质
- 越靠嘴说,长任务越靠不住:会话越长,早期指令的约束力越弱

**做法**:
- 划一条硬线:**风格与偏好 → 写文档;安全与不可逆 → 上强制**
- 强制手段:提交前钩子、命令拦截、fail-closed 门(检查不通过就不让过,而不是提示一下)
- 哪些动作必须进强制清单:删除/迁移/覆盖、直接推主干、跳过测试、动生产配置
- 强制的代价:过度强制会让 agent 卡死,给出松紧判据

**交付物**:**强制清单模板**(建议区 / 强制区 分栏)+ 一组可直接用的门禁检查项

**钩子**:单个会话稳住了,但一个大任务甩过去还是翻车——那是任务结构的问题,进第二阶。

## 第二阶 · 项目级可预期(04-07)

### 04 · 规格先行:把需求变成 agent 能验收的契约

**痛点场景**:"帮我把这个功能做完"——回来的东西能跑,但不是你要的;你解释一遍,它改一遍,又不是。

**为什么常规做法不 work**:
- 自然语言需求对人是够的,对 agent 不够:它缺的不是理解力,是**验收标准**
- 没有验收标准的任务,agent 只能猜"做到什么程度算完",猜错就是返工
- 圈内 2026 年的方向叫**规格驱动**(spec-driven):规格是真源,代码是规格的派生物

**做法**:
- 一份最小可用规格该写什么:输入输出、边界条件、明确不做什么、怎么算通过
- **"明确不做什么"是最省事的一栏**——它挡掉的返工比任何一栏都多
- 规格的可执行形态:能写成测试的就写成测试,写不成测试的写成检查清单
- 规格到实现的距离:什么程度算"照抄级",什么程度还留着让 agent 自己判断

**交付物**:**任务规格模板**(可直接放进项目当契约)

**钩子**:规格写清了,任务太大照样翻车。第 05 篇讲拆。

---

### 05 · 任务包拆分:大任务必然翻车的结构原因

**痛点场景**:一个中等功能扔过去,前半段做得挺好,后半段开始自相矛盾,最后收不了尾。

**为什么常规做法不 work**:
- 不是模型能力不够,是**一个任务包里塞了多个职责**,每个职责的验收标准互相干扰
- 任务越长,agent 越晚才发现前面做错了,返工成本呈非线性上涨
- "分步骤写清楚"不等于拆分:步骤还在同一个上下文里跑,失败会串联

**做法**:
- 一个任务包 = **单一职责交付物 + 独立验收标准**,两个条件缺一不可
- 拆分粒度判据:拆到"失败只影响这一包"为止;拆得太碎会在交接上把省下的时间还回去
- 依赖关系怎么表达:哪些能并行,哪些必须串行,怎么让 agent 自己知道
- 反例演示:一个真实的过大任务包,拆前拆后的对照

**交付物**:**任务包模板 + 拆分粒度判据清单**

**钩子**:拆开之后,你会发现不同的活该交给不同的工具。第 06 篇。

---

### 06 · 多工具分工:让每个 CLI 干它最擅长的那一段

**痛点场景**:订了好几个工具,但每个都当通用助手使,结果哪个都没用到点上,钱花了产能没上去。

**为什么常规做法不 work**:
- "哪个工具最强"是 2025 年的问题。2026 年的答案是**怎么分工**——圈内共识已经从选型转向编排
- 按"任务难度"分工是错的,应该按**决策密度**分:架构决策和机械执行,需要的根本不是同一种模型
- 每个工具都从零接手,交接处重复烧上下文

**做法**:
- 一套真实分工:谁做调研、谁做架构与设计、谁写码、谁做对抗审查、谁跑机械采集
- 交接契约:上游交出什么、下游必须收到什么才能开工,怎么传上下文而不重复烧
- 实测坑(这一节是真金白银换的):**模型 ID 静默漂移**——配了调不到的模型不报错、静默降级,你以为在用强模型其实不是;还有推理档位该不该为了省钱降档
- 并行择优什么时候值得,什么时候是纯浪费

**交付物**:**多工具分工对照表 + 调用规范**(含交接契约字段)

**钩子**:分工跑起来了,但产出对不对谁来判?不能是你自己。第 07 篇。

---

### 07 · 对抗审查:让 AI 挑自己的错,比你 review 更狠

**痛点场景**:改完让它"再检查一遍",它说"没问题"。你一看,问题就在那儿。

**为什么常规做法不 work**:
- "再检查一遍"是在要求它**确认自己**,模型会顺着自己的思路复述一遍,天然通不过对抗
- 换成"请你推翻这个结论"才有用:目标从确认变成否证
- 单个审查员不够——它只有一个视角,漏的正是它看不见的那类

**做法**:
- 提示词层面的一个关键转向:**默认站在"这是错的"这一侧**,让审查者需要举证才能放行
- 多镜头:正确性 / 安全 / 契约一致性,各派一个独立角色,互相不看对方结论
- 判定门槛:少数派否决还是多数通过,什么场景用哪个
- 验证循环:审查发现的问题必须能落成一条可复跑的检查,否则下次照样漏

**交付物**:**对抗审查提示词组**(三镜头 + 判定规则)

**钩子**:到这里项目级已经稳了。但下个项目你还得从头来一遍——第三阶解决这个。

## 第三阶 · 体系级复利(08-10)

### 08 · 问题不该聊完就散:把 bug 收口成台账

**痛点场景**:同一个坑,三个月内踩了两次。第二次踩的时候你甚至隐约觉得眼熟,但想不起上次怎么解的。

**为什么常规做法不 work**:
- "看到问题就开修"是最贵的路径:修完了知识留在会话里,会话一关就蒸发
- 聊天记录不是台账:检索不到、没有状态、没人复查
- 只写"这里坏了"不算问题定义,下次看还是不知道为什么坏

**做法**:
- 根因写三层:**现象 / 直接机制 / 系统设计缺口**。第三层才是防复发的那一层
- 补丁与解决的区别:只是临时绕开、加特判、降级而没补契约与测试的,只能标"止血",不能标"已解决"——这条规矩是防自欺的
- 什么值得开单,什么不值得(过度记录会把台账变成垃圾场)
- 单子和代码怎么挂上关系,让下次搜得到

**交付物**:**问题单模板 + 根因三层写法**(含"止血 vs 解决"判定)

**钩子**:台账解决了"同一个坑不踩两次"。但更大的浪费是——所有工具各自失忆。第 09 篇。

### 09 · 经验持久化:让所有 AI 工具共用同一个大脑

**痛点场景**:在 A 工具里花半小时教明白的事,换到 B 工具从零开始。换个项目,连 A 也不记得了。

> 这一篇是本系列的**账号验证选题**:同类主题在本号的点赞率是全站最高。说明这个痛点在这批读者里是真的。

**为什么常规做法不 work**:
- 每个工具自带的记忆是**工具私有**的,换工具即失忆,这是当前工具链公认的缺口
- 什么都往里存 = 什么都查不到:把仓库已经记录的东西(代码结构、git 历史)再写一遍是负资产
- 存了但 agent 读不到,等于没存

**做法**:
- 分类规则:什么该沉淀(踩过的坑、非显然的约定、外部资料指针),什么绝不沉淀(代码里已有的、只对这次会话有意义的)
- 一个可检索的个人知识层怎么搭:一条知识一个文件 + 一份索引,为什么这个结构比大文件好
- 怎么让 agent **自动**读到,而不是靠你每次贴
- 落档钩子:什么时机强制落档,否则永远"下次一起落"——而下次不会来

**交付物**:**知识沉淀分类规则 + 落档钩子配置**

**钩子**:知识能复用了,最后一步是把整套流程本身变成能力包。第 10 篇收尾。

### 10 · 把工作流打包成能力:从个人习惯到可分发资产

**痛点场景**:同一件事你已经跟 AI 交代了二十遍。每次都得重讲一遍背景、约定、注意事项。

**为什么常规做法不 work**:
- 反复交代的东西应该变成**能力包**,而不是每次重讲——但多数人卡在"不知道什么值得封装"
- 封装过度会僵化:把还在变的东西固化下来,后面改起来比不封装更贵
- 只有自己能用的能力包,维护成本迟早超过收益

**做法**:
- 能力包的边界判据:**重复三次以上 + 步骤稳定 + 有明确触发时机** 才值得封装
- 一个能力包该有什么:什么时候用它、按什么步骤走、边界在哪
- 从个人工作流到可分发资产:目录规范、命名、退役机制(能力包也会过期)
- 维护成本的真相:能力包不是零成本资产,给出一份自检清单

**交付物**:**能力包骨架 + 自检清单**

**收尾**:回到第 01 篇的能力自测表,重跑一遍。十项对照,这是这个系列唯一的验收标准。

## 四、执行要点

**篇幅**:每篇 2000-3000 字。9.9 元的系列不靠字数撑,靠"这一篇带走的东西下周就在用"。

**试读设置**:约前 20%,断点固定放在**"为什么常规做法不 work"讲完、正式做法开始之前**。让读者在断点处正好意识到自己一直做错了。

**免费篇**:第 01 篇公开。原因是本号的打赏信号极弱(158 篇里只有 3 篇有打赏,合计 20 元),付费转化必须靠能力证明,而不是靠情绪。

**排期**:周更 2 篇,5 周完结。**付费专辑读者可就未更新部分申请退款**,所以宁可慢也别断更——真断了是退款,不是掉粉。

**定价路径**:本系列 9.9 元做口碑底座。参考市场:同类小册 20-100 元、专栏/社群年费 100-400 元、系统课 300 元以上。下一系列可上 19.9-29.9。

**标题句式**(取自本季实测有效的四类):
1. **「不是 X,是 Y」** —— 推翻旧信念(用在 01)
2. **「为什么……照样不……」** —— 痛点共鸣(用在 03、05)
3. **「N 层 / N 阶 / 三层写法」** —— 结构可抄(用在 02、08)
4. **「让 AI 挑自己的错」** —— 反直觉动作(用在 07)

进阶开发者更愿付费的标题特征:**具体机制** > 泛"效率提升 10 倍";**失败场景** > 成功故事;**可抄结构** > 观点软文。

## 五、必须避开的坑

1. **不要写成工具说明书**。参数怎么填官方文档就有,读者付费买的是"该怎么组织"。
2. **不要每篇重讲基础概念**。系列内互相引用,重复铺垫是最明显的水分。
3. **交付物必须真跑过**。模板要是自己项目里在用的,不是现编的。
4. **不承诺省多少钱的具体数字**。个人用法差异大,给方法和自查工具,不给虚假承诺。
5. **不要把单源数据写成定论**。本次调研里"砍 80% 提示词不掉点""某负责人原话"这类都只有单一来源,写进文章时要么标注来源与不确定性,要么先在自己项目上复测。把单源当权威锚点是最容易被读者当场打脸的地方。
