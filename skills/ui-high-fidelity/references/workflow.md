# UI 高保真与可点原型工作流

## 目的与边界

把确认的交互和设计系统落实成逐 screen、逐状态、逐 viewport 的页面稿及可操作原型。静态截图用于视觉参考，不能证明点击路径可用。

## 最小输入

page/screen IDs、交互行为和状态矩阵、已授权视觉方向/设计系统，以及至少一条用户可走查的核心路径。独立调用允许从用户提供的现有页面与目标路径开始，记录缺失来源。

## 工作步骤

1. 按 screen ID 列出页面层级、密度和相邻页面节奏；检查全局导航、内容页、设置/表单页是否属于同一个产品体验。
2. 对内容量进行压力设计：标题/副标题的长短、长段落、极短摘要、空集合（0）、单项（1）、多项、边界数量。覆盖默认、展开、空、失败状态及 375px 移动视口；不要只用完美长度的占位文案。
3. 对表单稿补齐逐字段错误、整体失败、保存中、保存完成和权限失败；错误信息应贴近字段并说明修复动作。
4. 为每个适用 screen × state × viewport 编制 screen-specs.json 和可查看资产，依 shared ID registry 精确覆盖；asset_kind 使用 mock、design、render 或 prototype 区分产物类型。
5. 至少做一条可点原型：列出可操作链接/控件清单和入口路径，在高保真资产中使用 asset_kind=prototype 标出实际原型文件。
6. 实际操作原型，从入口开始点击到结果，记录返回、取消、空态和错误态的打开方式；把原型文件链接、访问方式和限制写入 high-fidelity.md。热点区域标注或一组截图不算可点原型。
7. 完整串联时在 stage 05 review 后快照，快照纳入引用资产；独立调用只交付页面稿/原型和走查路径。

## 产物

- high-fidelity.md：逐屏信息层级、组件、长短内容、响应方式、状态与原型操作路径。
- screen-specs.json：每条记录关联 screen_id/state_id/viewport_id、资产路径和 asset_kind。
- 可点击原型：可查看链接或本地文件，以及从入口到目标的操作步骤；记录运行环境和限制。

## 失败与回退

缺少交互决策时不要把视觉稿中的控件当产品承诺。设计工具不可用但能使用现有原型项目时，可在已授权环境中做可点击交付；如果用户要求图片/原型且没有任何可用方式，则标 blocked。仅有概念图时注明 concept/mock，不声称已能操作。

## 验收

- 核心路径至少一条在 prototype 文件中真实可点击，并有清楚起点、动作、反馈和终点。
- screen IDs、状态和 viewport 对齐注册表；内容压力集含 0/1/多项、长文本和字段错误等适用场景。
- 跨屏导航、正文密度、标题节奏一致；不是只完成 Hero。
- 点击走查证据和截图分开描述；截图不能替代原型操作路径。
