# UI/UX 架构工作流

## 目的与边界

把页面之间的关系和每个交互的前置条件、状态变化、反馈、恢复方式写清楚。交互契约先于视觉方向。可单独分析既有界面；完整套件才使用规范阶段目录和快照。

## 最小输入

至少需要一个具体用户任务或可检查的现有页面/路径；知道用户角色或权限时一并列出。若规则未知，区分已证实行为与设计建议。

## 工作步骤

1. 定义 page/screen 和路由：从哪个入口进入，完成、取消、返回或深链时去哪里。
2. 逐个交互记录顺序：触发条件 → 前置权限/数据检查 → 状态变化 → 用户反馈 → 失败后恢复/返回。各步需对应可见 UI 反馈。
3. 建状态矩阵：每个 screen × state × viewport 一行，区分适用和不适用；不适用必须有理由。基线至少考虑 default、loading、empty、error、permission_denied、success。
4. 明确取消与重入：取消后草稿/输入如何处理；重复提交是否禁用、去重或幂等；超时后显示什么，用户如何重试或检查真实结果。
5. 具体示例：表单保存需写“点保存→检查字段/权限→pending→成功提示并留在当前页”；若请求超时，显示“结果未确认”和再次检查入口，而不是先显示成功。
6. 绘制 wireframe，只标区域、内容顺序、控件及状态入口。此处不选择颜色、品牌字体或动效。
7. 写 ux-map.md、state-matrix.json、wireframes.md。完整串联时写 stage 02 的状态和审查；独立调用直接交付阶段文件，无需 snapshot。

## 产物

- ux-map.md：入口、路径、权限、触发/前置/状态/反馈/恢复/去向。
- state-matrix.json：与共享注册表同 ID，覆盖 screen × state × viewport。
- wireframes.md：每个 screen 的结构骨架及各关键状态如何呈现。

## 失败与回退

若权限、数据所有权或超时后端行为不明，不推断成功路径；标明责任方和待核问题。可先完成不受影响的纯浏览路径。旧页面行为若与新要求冲突，记录差异，不把观察值悄悄当成新决定。

## 验收

- 每条关键路径有入口、角色/权限、前置条件、状态、成功/失败反馈、恢复或返回路径。
- 取消、重复提交和超时均有明确约定，或记录为何不适用。
- 空状态和失败状态可区分；关键操作能用键盘表达或给出明确缺口。
- 独立流程可直接审查；完整流程的 IDs、状态和目录名符合共享契约。
