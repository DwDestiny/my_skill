# UI/UX 架构工作流

## 目的与边界

把用户旅程、页面之间的关系，以及每个交互的前置条件、状态变化、反馈、恢复方式和关键元素写清楚。交互契约先于视觉方向。可单独分析既有界面；完整套件才使用规范阶段目录和快照。

## 最小输入

至少需要一个具体用户任务或可检查的现有页面/路径；知道用户角色或权限时一并列出。若规则未知，区分已证实行为与设计建议。

## 工作步骤

1. 接收产品规划中的有序旅程和页面范围；若独立调用，则从用户给出的任务、现有页面或约束还原候选路径，并标注哪些来自事实、哪些是设计建议。
2. 确认每个范围内 page 至少被一条旅程覆盖；逐步定义 page/screen/state 和路由：从哪个入口进入，完成、取消、返回或深链时去哪里。发现孤立页面或未覆盖状态时，补路径或标为明确待定。
3. 逐个交互记录顺序：触发条件 → 前置权限/数据检查 → 状态变化 → 用户反馈 → 失败后恢复/返回。各步需对应可见 UI 反馈，并保留 journey step 与 page/screen/state 的追溯。
4. 建状态矩阵：每个 screen × state × viewport 一行，区分适用和不适用；不适用必须有理由。基线至少考虑 default、loading、empty、error、permission_denied、success。
5. 为每个适用状态列关键必需元素：可见内容、导航、操作控件和反馈；给元素稳定名称与角色。导航和交互控件应关联可复用组件定义；组件暂缺时记录待补，不删掉必需元素以绕过后续检查。
6. 明确取消与重入：取消后草稿/输入如何处理；重复提交是否禁用、去重或幂等；超时后显示什么，用户如何重试或检查真实结果。
7. 具体示例：表单保存需写“点保存→检查字段/权限→pending→成功提示并留在当前页”；若请求超时，显示“结果未确认”和再次检查入口，而不是先显示成功。
8. 绘制 wireframe，只标区域、内容顺序、控件及状态入口；检查必需元素都有位置和反馈方式。此处不选择颜色、品牌字体或动效。
9. 写 ux-map.md、state-matrix.json、wireframes.md。完整串联时写 stage 02 的状态和审查；独立调用直接交付阶段文件，无需 snapshot。字段形状与标识规则以共享交接契约为准。

## 产物

- ux-map.md：入口、用户旅程、步骤路径、权限、触发/前置/状态/反馈/恢复/去向；每个范围内页面有覆盖路径。
- state-matrix.json：与共享注册表同 ID，覆盖 screen × state × viewport，并列出各适用状态的关键必需元素。
- wireframes.md：每个 screen 的结构骨架、必需元素位置及各关键状态如何呈现。

## 失败与回退

若权限、数据所有权或超时后端行为不明，不推断成功路径；标明责任方和待核问题。可先完成不受影响的纯浏览路径。旧页面行为若与新要求冲突，记录差异，不把观察值悄悄当成新决定。

## 验收

- 每条关键路径有入口、角色/权限、前置条件、状态、成功/失败反馈、恢复或返回路径。
- 每条旅程步骤指向正确的 page、screen 和 state；无范围内孤立页面或无依据地遗漏的关键步骤。
- 每个适用状态的关键必需元素均在结构稿中有位置；导航和操作控件不会在页面间无故漂移。
- 取消、重复提交和超时均有明确约定，或记录为何不适用。
- 空状态和失败状态可区分；关键操作能用键盘表达或给出明确缺口。
- 独立流程可直接审查；完整流程的 IDs、状态和目录名符合共享契约。
