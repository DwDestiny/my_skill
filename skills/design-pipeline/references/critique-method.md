# 怎么看图：像设计师一样看截图

> 何时读：做完试样、做完每一轮实现、交付之前。
> 本文件教看图的方法。看图的目的是找到最该改的地方，不是确认"没问题"。
> 来源：2026-10-19 两次实测。两边的执行者每轮都写了"截图看过"，白环、歪按钮、焦点框、中间空白和整体方向的问题，最后都由用户指出。原因是看图时只找溢出、遮挡、报错，没有用下面这些看法。

## 1. 五种看法

每种看法看出一类问题。一轮看图至少用前三种。

| 看法 | 怎么做 | 看出什么 |
|---|---|---|
| 眯眼看 | 把截图缩到 25%，或模糊 8 px 再看 | 主次。缩小后还能认出的块，就是读者第一眼看到的。全是一样的灰块，说明没有主次 |
| 和锚点并排 | 把截图和锚点（用户认可过的页面，或设计源页面）左右并排，同宽同比例 | 水准差距和风格偏离。颜色冷暖、字重、留白、图片质感的差别，单看看不出，并排一眼就看出 |
| 放大看细节 | 放到 200%，看控件、图标按钮、标签、表单 | 对齐歪 1 px、两层底色形成的环、焦点框叠两道、文字基线跳动 |
| 走一遍状态 | 用键盘 Tab 走一遍；悬停每类可点元素；打开每个弹窗、下拉、tab；看空状态和加载 | 漏做的状态、默认样式残留、改版没覆盖到的 tab 和弹窗 |
| 找最平的一屏 | 按顺序看全部截图，指出最平淡的一屏 | 氛围在哪里掉了。最平的一屏通常在中段或最安静的一章 |

## 2. 写下最差的三处

看完以后，按"对用户目标影响最大"排序，写出最差的三处。每处写四件事：

1. **在哪里**：页面、区块、元素。
2. **看到什么**：具体现象，例如"搜索框外圈有一道 10 px 宽的白环"。
3. **为什么**：原因，例如"检索台暖白底和搜索框暖纸底之间有内边距"。
4. **怎么改**：具体做法，引用 `product-ui.md` 或 `direction-and-appeal.md` 的哪一节。

为什么要排序：小问题修得再多，最大的问题还在，页面就不会变好。团队页的复盘里，检查者看到了"中下段偏讲解、炫酷偏克制"，交回去修的却是白块和图标，方向问题留到了最后。

三处里有一处是方向问题（方向不吸引人、整页像说明书、和锚点差一个档次）时，先处理它：回阶段 2 重选方向或回阶段 3 重做这一屏。方向不对时修细节，只会把一个弱方向做得更完整。

## 3. 改完再看一次

改完重拍同一组截图，用同样的看法再看。写一句"这一轮最差的三处变成了什么"。连续两轮最差的一处没变，说明修法不对，换一种修法。

## 4. 测试通过说明什么

lint、类型检查、单元测试、构建通过，只说明功能没坏。`floor-check`、`defaults-check` 通过，只说明没有命中脚本能查的默认值。它们都不说明页面好看。报告里把这两类结果和看图结果分开写。
