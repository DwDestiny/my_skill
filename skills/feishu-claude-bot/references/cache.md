# 缓存：原理、验证、排查

## 1. 为什么要专门处理

每个飞书会话都是一个新的 `claude -p` 会话。Claude Code 只有工具定义和系统提示的静态部分能跨会话命中缓存。CLAUDE.md、skill 清单、记忆这些会话开头的上下文排在第一条用户消息前面，跟消息一起进缓存；消息每次不同，这一段（约 2 万 token）就每次重写。实测：不处理时一句“在吗”花 $0.18。

## 2. 模板已经做的四件事

1. **固定开场白**：新会话先用 `--session-id` 发一句固定的开场白，再用 `--resume` 发真正的消息。开场白每次相同，整段命中。新会话从 $0.18 降到约 $0.017，多 3–4 秒。`config.json` 的 `prime` 可关。
2. **`--exclude-dynamic-system-prompt-sections`**：把 cwd、环境、git 状态挪出系统提示。
3. **关 MCP**（`disable_mcp`）：MCP 异步连接，首个请求的工具列表时有时无，前缀跟着变。机器人需要某个 MCP 时，把 `disable_mcp` 设为 false 并接受缓存波动，或改写 `base_cmd()` 用 `--mcp-config` 只加载固定的几个并实测。
4. **前文放在缓存前缀之后**：前文拼在消息里，同一会话只补新增的，不影响前缀。

多个渠道（飞书、企微）共用同一套参数、守则和开场白，缓存前缀跨渠道共享；渠道差异只放在每条消息的消息头里。不要按渠道拆守则。

## 3. 验证

```bash
python3 bridge.py --cache-check 3
```

连开 3 个新会话，每个“开场白 + 一句测试消息”，打印缓存读/写。正常时：

| 轮次 | 开场白（读/写） | 测试消息（读/写） |
|---|---|---|
| 1 | 约 1.2 万 / 约 2.5 万 | 约 3.6 万 / 几十 |
| 2 | 约 3.6 万 / 0 | 约 3.6 万 / 几十 |
| 3 | 约 3.6 万 / 0 | 约 3.6 万 / 几十 |

第 1 轮写入多是正常的（新内容首次进缓存，或缓存已过期）。第 2 轮起开场白写入仍上万，就是前缀在变。

上线后：`grep cost logs/bridge.log`。`session_total` 是会话累计花费，不是单次。

## 4. 排查前缀为什么变

1. 用 `--system-prompt-snapshot on` 跑两个新会话，转录（`~/.claude/projects/<workdir 编码>/<session>.jsonl`）里会有 `api-request-shape` 和 `api-request-blob` 行。
2. 去掉会话 ID 后 diff 两个会话的这两类行，不同的地方就是原因。
3. 常见原因：MCP 工具列表变化；守则或开场白刚改过；CLAUDE.md、skill、记忆刚改过；插件更新。
4. 在主会话的 shell 里测，子进程会继承父会话的环境变量，结果可能和服务里不同。用 `systemd-run --user --pipe` 按服务同款环境复现。
