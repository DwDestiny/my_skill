# 边界：人设、身份、私密资料

## 1. 三层防线

| 层 | 管什么 | 靠什么 |
|---|---|---|
| 守则 `rules.md` | 什么能说、对谁说、什么事要主人点头 | Claude 自己判断 |
| 钩子 `lark_identity.py` | lark-cli 用哪个身份 | 硬拦，exit 2 |
| 钩子 `wecom_guard.py` | wecom-cli 能调什么 | 硬拦，exit 2 |
| 钩子 `private_guard.py` + 权限拒绝表 | 私密路径能不能读 | 硬拦 |

守则管“说不说”，钩子管“碰不碰”。能用钩子拦的就别只靠守则。

## 2. 场景怎么判断

bridge 给每次调用设环境变量，钩子据此判断：

| 变量 | 值 |
|---|---|
| `FCB_OWNER` | 1 = 发消息的是主人本人 |
| `FCB_PRIVATE` | 1 = 主人本人的私聊（只有这里放开私密资料） |
| `FCB_CHAT_ID` | 当前会话的 chat_id |
| `FCB_CHANNEL` | `feishu` / `wecom`，消息从哪个渠道来 |

主人在群里 @ 机器人，`FCB_PRIVATE` 仍是 0：群里有别人看着。非私聊场景还会设 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`，不读不写自动记忆。

## 3. 身份策略（config.json 的 identity）

| 字段 | 值 | 含义 |
|---|---|---|
| `owner` | `user_no_speak`（推荐） | 主人布置的事可以用主人身份办（日历、文档、会议室），但不能以主人名义发、改、撤消息 |
| | `user` | 完全放开 |
| | `bot` | 只用机器人身份 |
| `others` | `bot_read_im`（推荐） | 同事触发时，只有读聊天记录能用主人身份（机器人读不了群历史），其余只能用机器人身份 |
| | `bot` | 只用机器人身份；前文也读不到别的群 |

> **警告**：`bot_read_im` 下，同事 @ 机器人时，机器人能用主人身份读到主人和别人的私聊。挡住转述靠守则。主人对某些聊天有顾虑时，在 `lark_identity.py` 里加 chat_id 黑名单，或改用 `bot`。

### 企业微信（hooks/wecom_guard.py）

wecom-cli 带着主人的企微授权（读邮件、文档、日程、微盘），本机装了它，飞书会话也能调用。钩子总是挂上：主人本人发的可用，但不能以主人名义发消息和邮件；其他人只能用 `wecom-cli message aibot` 和 `wecom-cli contact`。细节见 [wecom.md](wecom.md) 第 4 节。

### 跨 IM 读取（config.json 的 cross_im_read）

两个渠道都启用时才有意义，默认关。

| | 关（默认） | 开 |
|---|---|---|
| 飞书会话读企微聊天记录（`wecom-cli chat`） | 拦 | 可以 |
| 企微会话用主人身份读飞书聊天记录（`lark-cli im +chat-messages-list` 等） | 拦 | 可以 |

开了以后，同事触发时能不能跨读，仍按 `identity.others`：`bot_read_im` 能读，`bot` 不能。

> **警告**：打开前要让主人确认：读到的内容会不会被转述到另一边，只靠守则和 Claude 把关。`scaffold.py` 第一次遇到打开的配置会打印提醒并停下，主人同意后加 `--confirm-cross-im` 再运行，确认记在实例的 `state/cross_im_confirmed`。

## 4. 旁听的权限

旁听由 bridge 用主人的用户身份定时拉白名单群的消息，所以：

- 主人必须在这个群里；`context.read_as` 是 `bot` 时旁听拉不到消息。
- 不需要开“读取群内所有消息”权限，非白名单群收不到任何没 @ 的消息。
- 旁听批次一律按“非主人、非私聊”跑（`FCB_OWNER=0`、`FCB_PRIVATE=0`），即使这批里有主人的发言，私密资料和主人身份都不放开。
- 只有主人能开关，命令在群里发，回复也只在那个群里。

## 4.1 长任务的权限

- 权限按派活人定，建任务时写进 `task.json`，之后谁补充指令都不变。同事派的活即使主人批了，也按“不是主人本人”跑：私密路径照拦，git 只能推 `bot/` 分支，gh 只能建草稿合并请求。
- 只有主人能批；补充指令、回答提问、取消只认主人和派活人本人（按发送人 ID）。
- 所有任务都不合并、不推主干、不发版。细节见 [tasks.md](tasks.md) 第 3 节。
- git 护栏挡得住直接的绕法，挡不住写脚本再执行这类间接绕法。主干要靠 GitHub 分支保护兜底。

## 5. 私密资料（config.json 的 private）

- `paths`：正则列表。工具参数里出现就拦。默认样例拦个人事项目录、`.private`、Claude 的会话转录和历史。
- `search_roots`：知识库这类“大部分能看、少数分区私密”的目录。对整个目录的 `rg`/`grep` 自动加排除规则；`Grep`/`Glob` 工具和 `find` 等不能对整个目录用，要么换 rg，要么指定子目录。

要问用户的：
1. 哪些目录完全私密？（个人事项、证件、合同）
2. 知识库里哪些分区不能给同事看？（人物页、日记、草稿、对公司的私下分析）
3. 有没有不能让机器人读的聊天？

实例目录本身（代码、钩子、配置、状态、日志）由 scaffold 逐项加进权限拒绝表，机器人不能改；`private_guard` 再兜住实例目录里新建的文件。唯一例外是守则：主人私聊里机器人能改（行为偏好如汇报频率、说话方式都写在守则里，主人一句话就能调），其他场景照样拦。守则不能进拒绝表，拒绝规则压过一切，主人私聊里也会被挡。

## 6. 人设边界要点

**工作分身**最容易犯的错是拦太多。第一个实例上线当天，守则里“公司、部门、同事的讨论不能露”被理解成连项目都不让聊，主人的反馈是“这就是个工作群”。正确的划分：

- 正常聊：需求、方案、代码、进度、排期、谁负责哪块、bug。
- 不外露：人物资料、对人和组织的私下评价与深挖分析、主人的私下立场、主人私事。
- 判断标准：“这句话被当事人或当事人的领导看到，主人会不会尴尬。”

**私人助理**反过来：默认什么都不对别人说，只有通用问题能聊。

两种人设都要写清“哪些事要主人点头”，并给出用机器人身份私聊主人的命令。
