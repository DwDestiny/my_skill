# UI 产品规划工作流

## 目的与边界

本阶段把产品目标转为有依据的用户旅程和完整页面范围。不决定视觉风格，不把视觉生成模型的填充内容当作真实产品事实。阶段可独立调用；若完整串联，按总交接契约写入规范目录并记录状态和快照。

## 最小输入

至少取得一项：用户描述的产品目标、某个具体任务、现存页面/流程，或要求评估的业务问题。尽量补齐目标用户与约束。缺少的内容标注为假设，不能伪造已有调研。

## 工作步骤

1. 将原始诉求拆成目标、用户、任务、成功信号、约束和“不做”事项；把事实、来源、推断和待确认项分列。
2. 盘点真实内容来源：用户素材、已存在业务数据、可引用的公开数据、或为演示而编造的概念内容。每种在页面清单注明；概念内容不可在 UI 中伪装成真实运行数据。
3. 从真实主任务整理有序用户旅程：标明起点、每步用户动作、预期结果和终点。关键任务、失败恢复与权限边界要有代表路径；推断的步骤单独标注，不能伪装成访谈事实。
4. 从旅程和用户任务推导信息结构：目标 → 需要的信息 → 模块 → page → screen → state → CTA/内容元素。每个模块说明支撑哪个任务；每个范围内页面至少出现于一条旅程。
5. 建立 CTA 优先级矩阵，至少列目标用户/任务、页面模块、主 CTA、次 CTA、成功信号和不可提供的动作。示例：导入完成后将“查看导入记录”设为主 CTA；不要同时把“升级套餐”设成同等视觉级别，除非商业目标明确。
6. 编制页面清单和入口，关联唯一 page ID、screen ID 与用户路径；列出适用的默认、加载、空、失败、权限拒绝、成功状态。为每个关键 state 识别页面必须呈现的内容、导航、操作和反馈元素，标明哪些是实现/验收必须逐项核对的元素。
7. 写 product-brief.md 与 page-inventory.json；记录目标、范围、旅程、关键假设、来源和决策。具体 JSON 路径、字段和枚举沿用共享交接契约，独立调用时可以用清楚的表格表达，不另造冲突 schema。
8. 完整串联时在 stage 01 目录提供 stage.json 并在审查后快照；独立调用只交付上述文件，不强制 stage/snapshot。

## 产物

- product-brief.md：产品目标、用户任务、成功信号、范围、非目标、事实来源、假设、风险和未决事项。
- page-inventory.json：契约规定的 pages/page IDs/screen IDs；不要自创第二套 ID。产品 brief 中保留有序旅程以及每个页面的目标任务、覆盖状态和关键必需元素的说明。
- CTA 优先级矩阵放在 brief 中，且逐项链接到页面和目标。

## 失败与回退

若连核心目标或主要用户都无法判断，输出已有证据和最小澄清问题并标记 blocked；不得用漂亮假设补齐业务。若只有部分场景已知，先交付有来源的部分，未知页面标为待定。独立运行可只分析已有页面，不要求完成全链。

## 验收

- 每个范围内 page 都至少由一条用户旅程覆盖；旅程有明确入口、顺序、结果和终点。
- 每个旅程步骤都可追溯到共享注册表中的 page、screen 和 state；不得以 Hero 截图或代表页代替全量范围。
- 每个关键 screen/state 的必需元素有稳定名称和用途，可传给 UX 阶段继续标注状态、角色和控件。
- 每个模块和 CTA 都能追溯到用户任务或明确商业约束。
- 真实/假设/演示内容有标注；真实用户资料的缺口不被假数据掩盖。
- 页面和 screen ID 与共享 delivery.json 一致；如 standalone 则不强制。
- 不把交付文件 validate 通过说成用户研究通过。
